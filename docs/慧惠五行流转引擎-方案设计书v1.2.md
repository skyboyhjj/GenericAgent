## 一、项目背景

### 1.1 慧惠项目简介

慧惠是一个面向个人用户的数字伴侣系统，基于 [GenericAgent](https://github.com/lsdefine/GenericAgent)（以下简称GA）构建。GA 是复旦大学团队开源的通用智能体框架，具备"上下文信息密度最大化"架构和五层记忆系统，其核心设计原则"无执行，无记忆"为可靠长期记忆的构建提供了坚实基础。

### 1.2 GA现有能力

GA 已具备的技能管理能力：

| 能力 | 实现方式 | 说明 |
|:---|:---|:---|
| 技能生长（木·生） | `start_long_term_update` 工具 + LLM蒸馏 | 成功执行的任务路径可结晶为SOP文件 |
| 记忆分层 | L0宪法→L1索引→L2事实→L3技能→L4归档 | 五层架构，信息密度递增 |
| 结晶触发 | LLM自主判断 | Agent在任务完成后自行决定是否调用蒸馏工具 |

### 1.3 GA的缺口

GA 论文明确承认："修剪/整合/迁移/更新需手工操作"。具体而言：

| 缺口 | 影响 |
|:---|:---|
| 无修剪机制 | 技能只增不减，记忆膨胀，检索效率下降 |
| 无整合机制 | 相似技能并存，存在冗余和矛盾 |
| 无迁移机制 | 技能绑定环境，无法跨场景复用 |
| 无更新机制 | 技能过期后仍被引用，导致执行失败 |
| 结晶触发不可控 | 依赖LLM自主决策，触发率低，产物质量无保障 |

### 1.4 项目动因

我们遵循《道德经》"为道日损"的哲学原则——**技能的生命不在于无限积累，而在于适时修剪、整合、迁移和更新**。这不仅是工程优化，更是数字生命的"呼吸"：吸（生）而不呼（克），终将窒息。

## 二、问题定义

### 2.1 核心问题

**GA的技能结晶是LLM的涌现行为，而非系统级的确定性机制。**

这一结论来自2026-05-03的专项验证测试（详见《GA技能结晶机制验证报告》），具体表现为两个层面的问题：

#### 问题P1：结晶触发不可靠

| 现象 | 数据 | 根因 |
|:---|:---|:---|
| 结晶触发率仅20% | 5个测试用例仅1个触发 | LLM默认倾向"不记"，需显式指令才触发 |
| 退出码不影响结晶决策 | exit_code=1时仍可触发 | LLM对"成功"的判断依赖主观感受而非系统信号 |
| L0规则被LLM解读过严 | "标准库用法无记忆价值" | LLM自行加码，将"不记录普通操作"泛化为"不记录简单任务" |

**唯一触发的条件**：任务指令中显式包含"记录下来"等记忆意图提示（`crystal_test_02`第4步）。

#### 问题P2：结晶产物质量不可控

| 现象 | 违反规则 | 根因 |
|:---|:---|:---|
| SOP含绝对路径 `D:\GenericAgent\temp\` | L0公理3：禁止易变状态 | LLM能读懂规则但不会100%遵守 |
| SOP含创建日期 `2026-05-03` | L0公理3：禁止易变状态 | 同上 |
| SOP缺少行动验证引用 | L0公理1：无执行无记忆 | LLM可能遗漏执行证据的引用 |

**结论**：LLM能读懂规则，但不保证执行规则。产物质量需要程序化校验，不能仅靠LLM自律。

### 2.2 问题的影响

| 影响维度 | 具体表现 |
|:---|:---|
| **可复现性** | 同类任务每次都要重新探索，无法利用历史经验 |
| **Token成本** | 重复探索导致Token消耗居高不下 |
| **记忆膨胀** | 无修剪机制，技能只增不减，长期运行后检索效率下降 |
| **产物可靠性** | 含易变状态的SOP在环境变更后失效，甚至误导Agent |
| **跨场景能力** | 技能绑定特定环境，无法迁移到新场景 |

## 三、设计目标

### 3.1 总体目标

在GA外部构建一套**可观测、可调控、可验证**的技能生命周期管理系统（五行流转引擎），使技能具备"生、克、化、通、变"的完整生命周期。

### 3.2 第一期目标（本次设计范围）

| 编号 | 目标 | 量化指标 |
|:---|:---|:---|
| G1 | 结晶触发确定性提升 | 触发率从20%提升至≥90% |
| G2 | 产物质量程序化保障 | L0公理违反率降至0% |
| G3 | 技能注册与可观测 | 所有SOP文件纳入Registry，元数据完整率100% |
| G4 | 技能修剪能力落地 | 90天未用/成功率<50%的技能自动归档 |

### 3.3 非目标（明确排除）

| 排除项 | 原因 |
|:---|:---|
| 修改GA核心代码 | 保持与上游兼容，降低维护成本 |
| 替换GA的结晶机制 | 在GA现有机制之上增强，不替代 |
| 实时跨设备同步 | 第三期先走"导出-导入"模式，实时同步留给第四期 |
| 火·化（技能整合） | 第二期详细设计见6.4 |
| 水·变（技能更新） | 第二期详细设计见6.6 |
| 土·通（技能迁移） | 第三期详细设计见6.7 |

## 四、设计原则

### 4.1 外挂增强，不改核心

所有改动以GA外部模块形式实现，GA核心代码（`ga.py`、`tools_schema.json`）仅做最小必要扩展（新增工具注册），不修改已有逻辑。

> 类比：给树浇水（外部滋养），而非嫁接（改基因）。

### 4.2 硬触发 + 硬校验，不依赖LLM自觉

关键路径不依赖LLM的"自觉"行为，而是通过程序化机制保障：
- 结晶触发：Agent Loop结束后自动注入蒸馏指令，而非等待LLM自主调用
- 产物校验：SOP写入后自动检测易变状态，而非依赖LLM遵守公理

> 类比：红绿灯（程序化）而非靠自觉让行。

### 4.3 成功即记录，筛选后置

结晶阶段放宽标准——凡是工具执行验证成功的任务路径，均应记录。筛选（克、化）放在后续阶段，而非在结晶阶段就做价值判断。

> 类比：先存粮，再筛糠。不在收割时决定哪些谷子值得留。

### 4.4 零侵入可回退

所有新增模块可通过配置开关独立启停。关闭后GA恢复原生行为，无残留影响。

> 类比：可拆卸的义肢，不是植入物。

### 4.5 五行框架对齐

所有模块命名和职责划分与"生克化通变"五行框架对齐，保持概念一致性，便于后续五行联调。

## 六、模块详细设计

### 6.1 WoodGrower（木·生增强）

**职责**：确保技能结晶的触发确定性和产物质量。

#### 6.1.1 自动蒸馏触发器

```python
# 文件：wuxing/wood_grower.py

class WoodGrower:
    """
    木·生增强：确保技能结晶的触发确定性
    
    设计依据：
    - 验证报告5.1：结晶是LLM涌现行为，需硬触发
    - 验证报告3.3：显式"记录下来"指令是唯一触发条件
    """
    
    CONFIG_DEFAULTS = {
        "enabled": True,               # 总开关
        "min_tool_calls": 3,           # 最少工具调用次数（低于此值不触发）
        "distill_prompt_template": ..., # 蒸馏指令模板
        "post_validate": True,         # 是否启用产物校验
    }
    
    def auto_trigger(self, turn_history: list[dict], messages: list[dict]) -> bool:
        """
        Agent Loop结束后调用。判断是否需要触发蒸馏，并注入蒸馏指令。
        
        参数：
            turn_history: 本轮对话中所有工具调用的记录
            messages: 消息队列（用于追加蒸馏指令）
        
        返回：
            True: 已注入蒸馏指令
            False: 未触发（工具调用次数不足）
        
        逻辑：
            1. 统计turn_history中成功的工具调用次数
            2. 若 < min_tool_calls，返回False
            3. 构造蒸馏指令，追加到messages
            4. 返回True，让Agent Loop继续执行一轮
        """
        ...
    
    def post_validate(self, sop_path: str) -> ValidationResult:
        """
        SOP写入后调用。程序化校验产物质量。
        
        校验规则：
            R1: 禁止绝对路径 — 正则匹配 [A-Z]:\\ 或 /home/ 或 /Users/
            R2: 禁止日期格式 — 正则匹配 \d{4}-\d{2}-\d{2}
            R3: 禁止环境特定值 — 检测 /usr/、/opt/、C:\\Users\\
            R4: 必须有行动验证引用 — 检测是否引用了工具执行结果
        
        返回：
            ValidationResult(passed, violations, auto_fixes)
        
        自动修复：
            - 绝对路径 → 替换为相对路径描述
            - 日期 → 删除该行
            - 环境特定值 → 替换为通用描述
        """
        ...
```

#### 6.1.2 蒸馏指令模板

```python
DISTILL_PROMPT_TEMPLATE = """
Task completed successfully. IMPORTANT SYSTEM INSTRUCTION:

You MUST call start_long_term_update tool now to crystallize this execution path.

Rules for crystallization:
1. Record the validated steps that led to successful task completion
2. Do NOT include any absolute paths (e.g., D:\\..., /home/...)
3. Do NOT include any dates (e.g., 2026-05-03)
4. Do NOT include any environment-specific values
5. DO include references to which tools were called and what they returned
6. Follow memory_management_sop.md Axiom 1 (no execution = no memory) 
   and Axiom 3 (no mutable state) STRICTLY

This is a mandatory system requirement, not optional.
"""
```

**设计考量**：指令中同时包含"做什么"（必须调用工具）和"怎么做"（遵守L0公理），双管齐下——即使LLM忽略公理，`post_validate`也会兜底。

#### 6.1.3 产物校验规则详解

| 规则 | 检测方式 | 自动修复 | 依据 |
|:---|:---|:---|:---|
| R1: 禁止绝对路径 | `[A-Z]:\\{1,2}\S+` 或 `/home/\S+` 或 `/Users/\S+` | 替换为`<relative_path>` | L0公理3 |
| R2: 禁止日期 | `\d{4}[-/]\d{2}[-/]\d{2}` | 删除该行 | L0公理3 |
| R3: 禁止环境特定值 | `/usr/\S+`、`/opt/\S+`、`C:\\Users\\\S+` | 替换为`<system_path>` | L0公理3 |
| R4: 必须有行动验证引用 | 检测`tool_call`、`execution`、`verified`等关键词 | 标记为warning，不自动修复 | L0公理1 |

**R4的特殊处理**：如果SOP中完全没有行动验证引用，标记为warning但不阻止注册——因为LLM可能用不同措辞描述执行证据，强行检测可能误判。

### 6.3 MetalRestrainer（金·克修剪）

**职责**：评估技能健康度，自动归档低健康度技能。

#### 6.3.1 健康度模型

```
health = w1 × freshness + w2 × reliability + w3 × complexity_bonus

其中：
  freshness    = exp(-λ × days_since_last_use)    # 新鲜度衰减
  reliability  = success_rate                      # 可靠性（成功率）
  complexity_bonus = min(tool_count / 5, 1.0)      # 复杂度加分（多工具技能更有价值）

默认权重：
  w1 = 0.4（新鲜度权重最高——不用的技能最应该被修剪）
  w2 = 0.4（可靠性其次——总失败的技能是负担）
  w3 = 0.2（复杂度最低——但多工具编排技能值得多留一会）

衰减参数：
  λ = 0.02（半衰期约35天——35天不用健康度降至0.5）
```

**健康度曲线示意**：

```

  1.0 ┤━━━━━━━━━━━━━╲
  0.8 ┤              ╲━━━━━━━━━━━━━
  0.6 ┤                            ╲━━━━━━━
  0.4 ┤                                    ╲━━━━
  0.2 ┤    (success_rate=0.5)                    ╲━
  0.0 ┤━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
      0     30     60     90    120    150   days
                          ↑
                    归档阈值(0.3)
```

### 6.4 FireTransformer（火·化整合）

**职责**：检测相似技能，合并冗余SOP，提升技能库的信息密度。

#### 6.4.1 设计哲学

> "万物负阴而抱阳，冲气以为和。"——《道德经》第42章

火·化的核心不是"消灭冗余"，而是"冲气以为和"——将分散的、重叠的经验融合为更完整、更通用的知识。两个相似技能的存在不是问题，而是整合的契机：它们各自覆盖了同一领域的不同侧面，合并后的产物应比任何一个原始技能都更强大。

#### 6.4.2 相似度检测模型

相似度检测采用**多信号融合**策略，而非单一维度判断：

```
similarity = α × tag_similarity + β × tool_overlap + γ × semantic_similarity

其中：
  tag_similarity    = |tags_A ∩ tags_B| / |tags_A ∪ tags_B|      # Jaccard系数
  tool_overlap      = |tools_A ∩ tools_B| / |tools_A ∪ tools_B|   # 工具调用重叠度
  semantic_similarity = LLM_judgment(A, B)                         # LLM语义判断 [0,1]

默认权重：
  α = 0.25（标签信号较粗糙，权重较低）
  β = 0.35（工具调用是技能本质特征，权重最高）
  γ = 0.40（语义判断最精准但成本最高，权重最高）
```

**三层漏斗检测流程**：

```
Layer 1: 标签快筛（零成本）
  计算所有技能对的 tag_similarity
  过滤 tag_similarity < 0.2 的对（明确不相似）
  ↓ 候选对数量大幅减少

Layer 2: 工具交叉验证（低成本）
  对候选对计算 tool_overlap
  过滤 tool_overlap < 0.3 的对（工具集差异过大）
  ↓ 候选对进一步减少

Layer 3: LLM语义判断（高成本，仅对少量候选对）
  对剩余候选对调用LLM进行语义相似度判断
  综合三信号计算最终 similarity
  similarity ≥ merge_threshold (默认0.7) → 进入合并流程
```

**Layer 3 LLM判断Prompt模板**：


#### 6.4.3 合并策略

当两个技能的相似度 ≥ `merge_threshold` 时，有三种合并策略：

| 策略 | 适用条件 | 操作 | 示例 |
|:---|:---|:---|:---|
| **absorb_a** | A是B的超集，B只是A的特例 | A吸收B的差异化内容，B归档 | `file_search`（通用）吸收 `txt_search`（特例） |
| **absorb_b** | B是A的超集 | B吸收A，A归档 | 反向 |
| **create_new** | A和B交叉，各自有独特内容 | 创建新SOP，两者均归档 | `stock_query` + `fund_query` → `finance_query` |

**合并执行流程**：

```python
# 文件：wuxing/fire_transformer.py

class FireTransformer:
    """
    火·化整合：检测相似技能，合并冗余SOP
    
    设计原则：
    - 冲气为和：合并不是消灭，而是让两份经验的"气"冲融为更完整的知识
    - 多信号融合：不依赖单一维度判断相似性
    - 保守合并：宁可漏合，不可错合——错误合并的代价远高于保留冗余
    - 可追溯：合并历史完整记录，支持拆分回退
    """
    
    CONFIG_DEFAULTS = {
        "enabled": True,
        "merge_threshold": 0.7,       # 相似度高于此值触发合并
        "tag_filter_threshold": 0.2,  # Layer1 标签快筛阈值
        "tool_filter_threshold": 0.3, # Layer2 工具交叉验证阈值
        "weights": {0.25, 0.35, 0.40}, # α, β, γ
        "auto_merge": False,          # True=自动合并, False=需人工确认
        "llm_model": None,            # 用于语义判断的LLM模型（None=使用GA默认）
        "dry_run": False,             # 只报告不执行
    }
    
    def scan(self, registry: SkillRegistry) -> list[MergeCandidate]:
        """
        扫描所有active技能，识别需要合并的技能对。
        
        三层漏斗流程：
        1. 标签快筛：Jaccard相似度过滤
        2. 工具交叉验证：工具调用集重叠度过滤
        3. LLM语义判断：最终相似度评分
        
        返回：MergeCandidate列表，按相似度降序排列
        """
        ...
    
    def propose(self, candidate: MergeCandidate) -> MergeProposal:
        """
        生成合并提案。
        
        包含：
        - 两个SOP的对比摘要（摘要由LLM生成）
        - 推荐合并策略（absorb_a / absorb_b / create_new）
        - 合并后的预期收益
        - 风险评估（是否有信息丢失的风险）
        
        返回：MergeProposal，可展示给用户确认或自动执行
        """
        ...
    
    def merge(self, proposal: MergeProposal, registry: SkillRegistry) -> MergeResult:
        """
        执行合并。
        
        步骤：
        1. 调用LLM生成合并后的SOP内容
        2. post_validate校验合并产物（复用WoodGrower的校验规则）
        3. 如果校验失败，尝试自动修复
        4. 写入新SOP文件
        5. 更新registry：
           - 新技能注册（merged_from字段记录来源）
           - 旧技能标记为merged（非archived，区分"被合并"和"被淘汰"）
        6. 旧SOP文件移至archive/merge_history/
        7. L1索引更新
        8. 记录合并历史
        
        返回：MergeResult（成功/失败、新skill_id、合并产物路径）
        """
        ...
    
    def split(self, merged_skill_id: str, registry: SkillRegistry) -> SplitResult:
        """
        拆分已合并的技能（反悔机制）。
        
        步骤：
        1. 从registry读取merged_from字段，获取原始技能ID列表
        2. 从archive/merge_history/恢复原始SOP文件
        3. 删除合并后的SOP
        4. registry中恢复原始技能条目
        5. L1索引恢复
        6. 记录拆分历史
        
        返回：SplitResult
        """
        ...
```

| R7: 通用性提升 | 合并产物应比任一原始SOP覆盖更多场景 | 合并的目的是"冲气为和"，不是简单拼接 |

| 触发方式 | 条件 | 场景 |
|:---|:---|:---|
| **定期扫描** | InternalAuditor每周审计时调用`FireTransformer.scan()` | 常规维护 |
| **新技能注册时** | 新SOP注册后，立即与现有技能做相似度检测 | 及时发现重复 |
| **手动触发** | 用户显式要求"检查是否有重复技能" | 人工干预 |
| **阈值触发** | active技能数量超过`max_skills_before_merge`（默认30） | 防止膨胀 |

**新技能注册时的增量检测**（性能优化）：

```python
def scan_incremental(self, new_skill_id: str, registry: SkillRegistry) -> list[MergeCandidate]:
```

#### 6.4.8 合并冲突处理

当两个SOP存在操作冲突时（例如同一操作用不同参数），LLM合并产物中应采用**条件分支**而非二选一：


### 6.6 WaterTransformer（水·变更新）

**职责**：检测技能是否过期，自动回放验证，修复失效步骤，维护技能的时效性。

#### 6.6.1 设计哲学

> "上善若水。水善利万物而不争。"——《道德经》第8章

水·变的核心是"不争而善变"——技能不是一成不变的化石，而是活的水流。当外部环境变化（API升级、依赖版本更迭、路径变更）导致技能失效时，水·变不是抛弃旧技能重新来过，而是像水一样——找到新的路径，绕过障碍，继续流淌。

与金·克的区别：金·克是"此路已废，换一条"，水·变是"此路不通，修一修"。

#### 6.6.2 过期检测机制

技能过期的判定不是简单的"时间太久"，而是基于多维信号的**综合衰退评估**：

```
staleness = w_t × time_factor + w_f × fail_factor + w_e × env_change_factor

其中：
  time_factor     = min(days_since_validate / validate_cycle, 1.0)
                    # 距上次验证的天数 / 验证周期（默认30天），上限1.0
  fail_factor     = recent_fail_rate
                    # 近N次使用的失败率（N默认5）
  env_change_factor = detected_env_changes / total_dependencies
                    # 检测到的环境变更数 / 技能依赖总数

默认权重：
  w_t = 0.3（时间是间接信号，权重较低）
  w_f = 0.5（失败率是直接信号，权重最高）
  w_e = 0.2（环境变更是辅助信号，需要额外检测成本）
```

**staleness阈值**：

| staleness | 判定 | 动作 |
|:---|:---|:---|
| < 0.3 | 健康 | 无需验证 |
| 0.3 ~ 0.6 | 可疑 | 标记为warning，下次审计时回放验证 |
| ≥ 0.6 | 过期 | 立即触发回放验证 |

#### 6.6.3 环境变更检测

自动检测以下环境变更信号，作为`env_change_factor`的输入：

| 检测项 | 方法 | 成本 |
|:---|:---|:---|
| Python依赖版本变更 | `pip list --format=json` 对比快照 | 低 |
| 系统路径变更 | `sys.path`、`PATH` 环境变量对比 | 低 |
| API可用性变更 | 对SOP中引用的外部URL做HEAD请求 | 中 |
| 文件系统变更 | SOP中引用的文件路径是否存在性检查 | 低 |
| GA版本变更 | 对比当前版本号与上次验证时记录的版本号 | 低 |

#### 6.6.4 回放验证流程

回放验证是水·变的核心——它不是简单地"看一眼SOP"，而是**实际执行SOP中描述的步骤**，验证每一步是否仍然成功。

```python
# 文件：wuxing/water_transformer.py

class WaterTransformer:
    """
    水·变更新：检测技能过期，回放验证，自动修复
    
    设计原则：
    - 不争而善变：修复优先于抛弃，只有修复失败才走金·克
    - 实证为王：回放验证是判断技能是否过期的唯一可靠方式
    - 最小修复：只修复失效的步骤，不重写整个SOP
    - 版本可回溯：每次更新生成新版本，旧版本保留
    """
    
    CONFIG_DEFAULTS = {
        "enabled": True,
        "validate_cycle_days": 30,       # 验证周期（天）
        "staleness_threshold": 0.6,      # 过期阈值
        "warning_threshold": 0.3,        # 可疑阈值
        "recent_fail_window": 5,         # 计算近期失败率的窗口大小
        "max_repair_attempts": 2,        # 最大修复尝试次数
        "auto_repair": False,            # True=自动修复, False=需人工确认
        "dry_run": False,                # 只报告不执行
    }
    
    def detect_stale(self, registry: SkillRegistry) -> list[StaleReport]:
        """
        检测所有active技能的staleness。
        
        流程：
        1. 遍历registry中所有active技能
        2. 计算每个技能的staleness分数
        3. staleness ≥ warning_threshold的标记为候选
        4. 返回按staleness降序排列的报告
        
        返回：StaleReport列表
        """
        ...
    
    def replay_validate(self, skill_id: str, registry: SkillRegistry) -> ReplayResult:
        """
        对单个技能执行回放验证。
        
        流程：
        1. 读取SOP文件，解析出可执行的步骤
        2. 构造一个最小化的回放指令，注入到GA中执行
        3. 监控执行过程，记录每一步的成功/失败
        4. 如果全部成功 → 更新validated_at，staleness归零
        5. 如果某步失败 → 记录失败步骤和错误信息
        
        回放指令构造：
        - 从SOP中提取"步骤"章节
        - 用最小参数构造执行指令（如用默认symbol="000001"测试股票查询）
        - 不产生副作用（查询类任务天然安全；修改类任务需特殊处理）
        
        返回：ReplayResult（passed/failed, failed_steps, error_messages）
        """
        ...
    
    def repair(self, skill_id: str, replay_result: ReplayResult, 
               registry: SkillRegistry) -> RepairResult:
        """
        对验证失败的技能执行LLM修复。
        
        流程：
        1. 将原始SOP + 失败步骤 + 错误信息 组装为修复Prompt
        2. 调用LLM生成修复后的SOP
        3. post_validate校验修复产物
        4. 对修复产物再次回放验证
        5. 如果验证通过 → 更新SOP文件，版本号+1
        6. 如果验证失败 → 记录失败，考虑再次修复或标记为deprecated
        
        修复策略：
        - 最小修复：Prompt中明确要求"只修改失败的步骤，保留其他步骤不变"
        - 渐进修复：每次只修复一个失败步骤，而非一次性重写
        - 成本控制：max_repair_attempts限制修复轮次
        
        返回：RepairResult（success, new_version, repaired_steps）
        """
        ...
    
    def mark_deprecated(self, skill_id: str, registry: SkillRegistry) -> None:
        """
        将修复失败的技能标记为deprecated。
        
        deprecated ≠ archived：
        - archived：被金·克淘汰（不健康/不用）
        - deprecated：被水·变确认失效（修不好）
        
        deprecated的技能：
        - 仍在L3中（不移至archive/）
        - registry中status改为deprecated
        - L1索引保留但标注"[已失效]"
        - 仍可被lookup搜到，但Agent会看到失效标记
        """
        ...
```

### 6.7 EarthMigrator（土·通迁移）

**职责**：评估技能的环境兼容性，将技能适配到新环境，实现跨场景复用。

#### 6.7.1 设计哲学

> "大道泛兮，其可左右。"——《道德经》第34章

土·通的核心是"泛"——技能不应被绑定在一个特定环境中。好的技能像大道一样，可以"左右"——在不同的操作系统、Python版本、依赖配置之间自由流动。土·通不是简单复制，而是**适配**——像土壤中的养分，因植物的不同而调整形态，但本质不变。

与水·变的区别：水·变是"同一环境下的修复"，土·通是"跨环境的适配"。

#### 6.7.2 环境画像

每个GA实例都有一个**环境画像（Environment Profile）**，描述技能运行所需的上下文：

#### 6.7.3 兼容性评估模型

当技能需要迁移到新环境时，先做兼容性评估：

```
compatibility = Σ(w_i × check_i) / Σw_i

其中每个check_i是独立的兼容性检查项：
```

| 检查项 | 方法 | 权重 | 通过条件 |
|:---|:---|:---|:---|
| OS兼容性 | SOP中的命令是否适配目标OS | 0.2 | 无OS特有命令，或SOP已有条件分支 |
| Python版本兼容性 | SOP中的语法/API是否适配目标版本 | 0.15 | 无版本特有语法 |
| 依赖可用性 | SOP中的依赖是否在目标环境已安装 | 0.30 | 全部依赖已安装或可安装 |
| 路径兼容性 | SOP中的路径是否适配目标环境 | 0.15 | 使用相对路径或已有环境变量 |
| API可达性 | SOP中的外部API是否在目标环境可访问 | 0.10 | 全部API可达 |
| 工具可用性 | SOP中使用的GA工具在目标环境是否可用 | 0.10 | 全部工具可用 |

**依赖可用性权重最高（0.30）**，因为这是最常见的迁移障碍。

**兼容性判定**：

| compatibility | 判定 | 动作 |
|:---|:---|:---|
| ≥ 0.8 | 绿灯 | 直接迁移，无需适配 |
| 0.5 ~ 0.8 | 黄灯 | 需要适配，调用LLM生成适配版本 |
| < 0.5 | 红灯 | 不建议迁移，差距过大 |

#### 6.7.4 迁移执行流程

```python
# 文件：wuxing/earth_migrator.py

class EarthMigrator:
    """
    土·通迁移：评估技能环境兼容性，将技能适配到新环境

    - 泛而不散：迁移不是简单复制，而是适配
    - 实证验证：迁移后的技能必须在新环境中回放验证
    - 最小适配：只修改环境相关的部分，不改核心逻辑
    - 双向记录：源环境和目标环境都保留迁移记录
    """
    
    CONFIG_DEFAULTS = {
        "enabled": True,
        "green_threshold": 0.8,         # 绿灯阈值
        "yellow_threshold": 0.5,        # 黄灯阈值（低于此为红灯）
        "auto_migrate": False,          # True=绿灯自动迁移, False=需确认
        "post_migrate_validate": True,  # 迁移后是否自动回放验证
        "dry_run": False,               # 只报告不执行
    }
    
    def assess(self, skill_id: str, target_profile: EnvironmentProfile, 
               registry: SkillRegistry) -> CompatibilityReport:
        """
        评估技能在目标环境中的兼容性。
        
        流程：
        1. 读取技能SOP和源环境画像
        2. 逐项检查兼容性（6项检查）
        3. 计算综合兼容性分数
        4. 判定绿灯/黄灯/红灯
        5. 对于不通过的项目，给出适配建议
        
        返回：CompatibilityReport
        """
        ...
    
    def adapt(self, skill_id: str, compat_report: CompatibilityReport,
              target_profile: EnvironmentProfile, 
              registry: SkillRegistry) -> AdaptResult:
        """
        将技能适配到目标环境（黄灯场景）。
        
        流程：
        1. 将原始SOP + 兼容性报告 + 适配建议 组装为适配Prompt
        2. 调用LLM生成适配版本
        3. post_validate校验适配产物
        4. 写入新SOP文件（带环境后缀，如stock_query_linux_sop.md）
        5. registry中注册新技能，标记为原技能的变体
        
        返回：AdaptResult（success, new_skill_id, adapted_sop_path）
        """
        ...
    
    def migrate(self, skill_id: str, target_profile: EnvironmentProfile,
                registry: SkillRegistry) -> MigrateResult:
        """
        执行完整的迁移流程。
        
        流程：
        1. 兼容性评估
```

#### 6.7.7 跨设备同步场景

土·通的一个典型应用场景是：**妙秒在办公电脑上积累了技能，回家后想在笔记本上复用**。

```
┌──────────────────┐              ┌──────────────────┐
│   办公电脑         │              │   家用笔记本       │
│ (Windows 11)      │              │ (macOS)           │
│                   │   迁移        │                   │
│ stock_query_sop   │────────────→│ stock_query_mac   │
│ check_files_sop   │  (土·通适配) │ _sop              │
│ web_scrape_sop    │              │ check_files_mac   │
│                   │              │ _sop              │
│ env_profile:      │              │ env_profile:      │
│ miaomiao_work     │              │ miaomiao_home     │
│ station           │              │                   │
└──────────────────┘              └──────────────────┘
        │                                  │
        └────────  Sophub 同步 ─────────────┘
```

**同步方式**（第一版简化方案）：

1. 通过Sophub平台导出技能包（含SOP + Registry元数据 + env_profile）
2. 在目标设备导入技能包
3. EarthMigrator自动评估兼容性并适配
4. 适配后回放验证

**后续版本**可考虑实时同步（类似iCloud），但第一版先走"导出-导入"模式，降低实现复杂度。

#### 6.7.8 土·通的触发时机

| 触发方式 | 条件 | 场景 |
|:---|:---|:---|
| **导入技能包时** | 检测到新环境，自动触发兼容性评估 | 跨设备同步 |
| **环境变更时** | 当前环境画像发生重大变更（如OS升级） | 批量重新评估 |
| **定期审计** | InternalAuditor每月审计时检查环境画像变更 | 常规维护 |
| **手动触发** | 用户要求"把我的技能迁移到另一台电脑" | 人工干预 |

### 7.2 健康度计算公式

$$
H = w_f \cdot e^{-\lambda \cdot d} + w_r \cdot s + w_c \cdot \min\left(\frac{t}{5}, 1\right)
$$

| 符号 | 含义 | 默认值 |
|:---|:---|:---|
| $H$ | 健康度 | [0, 1] |
| $d$ | 距上次使用的天数 | — |
| $\lambda$ | 新鲜度衰减率 | 0.02 |
| $s$ | 成功率 | success_count / use_count |
| $t$ | 工具调用次数（复杂度代理） | — |
| $w_f$ | 新鲜度权重 | 0.4 |
| $w_r$ | 可靠性权重 | 0.4 |
| $w_c$ | 复杂度权重 | 0.2 |

**边界情况处理**：

| 情况 | 处理方式 |
|:---|:---|
| use_count = 0（从未复用） | freshness = 1.0, reliability = 0.5（中性默认值） |
| success_rate = null | 使用0.5作为默认值 |
| days_since_last_use = null | 使用days_since_created |

### 7.3 相似度计算公式

$$
S_{ij} = \alpha \cdot \frac{|T_i \cap T_j|}{|T_i \cup T_j|} + \beta \cdot \frac{|P_i \cap P_j|}{|P_i \cup P_j|} + \gamma \cdot L(A_i, A_j)
$$

| 符号 | 含义 | 默认值 |
|:---|:---|:---|
| $S_{ij}$ | 技能i与技能j的相似度 | [0, 1] |
| $T_i$ | 技能i的标签集合 | — |
| $P_i$ | 技能i的工具调用集合 | — |
| $L(A_i, A_j)$ | LLM对两技能SOP内容的语义相似度判断 | [0, 1] |
| $\alpha$ | 标签相似度权重 | 0.25 |
| $\beta$ | 工具重叠度权重 | 0.35 |
| $\gamma$ | 语义相似度权重 | 0.40 |

**三层漏斗的过滤阈值**：

| 层级 | 阈值 | 说明 |
|:---|:---|:---|
| Layer 1: 标签快筛 | $\frac{|T_i \cap T_j|}{|T_i \cup T_j|}$ < 0.2 → 排除 | 零成本，快速过滤 |
| Layer 2: 工具交叉 | $\frac{|P_i \cap P_j|}{|P_i \cup P_j|}$ < 0.3 → 排除 | 低成本，进一步收窄 |
| Layer 3: LLM语义 | $S_{ij}$ ≥ 0.7 → 进入合并 | 高成本，仅对少量候选对执行 |

### 7.4 过期度计算公式

$$
Staleness = w_t \cdot \min\left(\frac{d_{val}}{C}, 1\right) + w_f \cdot f_{recent} + w_e \cdot \frac{n_{change}}{n_{dep}}
$$

| 符号 | 含义 | 默认值 |
|:---|:---|:---|
| $d_{val}$ | 距上次验证的天数 | — |
| $C$ | 验证周期（天） | 30 |
| $f_{recent}$ | 近N次使用的失败率 | — |
| $n_{change}$ | 检测到的环境变更数 | — |
| $n_{dep}$ | 技能依赖总数 | — |
| $w_t$ | 时间因子权重 | 0.3 |
| $w_f$ | 失败率权重 | 0.5 |
| $w_e$ | 环境变更权重 | 0.2 |

**staleness判定阈值**：

| staleness | 判定 | 动作 |
|:---|:---|:---|
| < 0.3 | 健康 | 无需验证 |
| 0.3 ~ 0.6 | 可疑 | 标记warning，下次审计回放 |
| ≥ 0.6 | 过期 | 立即回放验证 |

### 7.5 兼容性计算公式

$$
Compat = \frac{\sum_{i=1}^{6} w_i \cdot check_i}{\sum_{i=1}^{6} w_i}
$$

| 检查项 $i$ | 权重 $w_i$ | 通过条件 |
|:---|:---|:---|
| OS兼容性 | 0.20 | 无OS特有命令或已有条件分支 |
| Python版本兼容性 | 0.15 | 无版本特有语法 |
| 依赖可用性 | 0.30 | 全部依赖已安装或可安装 |
| 路径兼容性 | 0.15 | 使用相对路径或已有环境变量 |
| API可达性 | 0.10 | 全部API可达 |
| 工具可用性 | 0.10 | 全部工具可用 |

**compatibility判定阈值**：

| compatibility | 判定 | 动作 |
|:---|:---|:---|
| ≥ 0.8 | 绿灯 | 直接迁移 |
| 0.5 ~ 0.8 | 黄灯 | LLM适配后迁移 |
| < 0.5 | 红灯 | 不建议迁移 |

```python
# 原有代码：当模型没有工具调用时退出
if not response.tool_calls:
    # 【新增】尝试自动触发蒸馏
    if wood_grower.auto_trigger(turn_history, messages):
        # 继续循环，让LLM处理蒸馏指令
        continue
    
    # 【新增】检查是否有新SOP需要注册
    new_sops = detect_new_sops(pre_snapshot, post_snapshot)
    for sop in new_sops:
        # 产物校验
        result = wood_grower.post_validate(sop)
        if result.passed:
            skill_id = registry.register(sop, metadata={"created_turn": turn})
            # 新技能注册后立即做增量相似度检测
            candidates = fire_transformer.scan_incremental(skill_id, registry)
            if candidates and candidates[0].overall_similarity >= fire_transformer.merge_threshold:
                # 发现高相似度技能，自动生成合并提案（但不自动执行）
                proposal = fire_transformer.propose(candidates[0])
                # 记录提案，等待审计时处理或人工确认
                log_merge_proposal(proposal)
        else:
            # 校验失败，尝试自动修复后重新注册
            if result.auto_fixes:
                registry.register(sop, metadata={"created_turn": turn, "auto_fixed": True})
    
    break

# ─── 在GA启动时（非Agent Loop内）───
# 检查环境画像是否变更，如有变更触发水·变检测
current_profile = EarthMigrator.load_current_profile()
if current_profile.changed_since_last_run():
    stale_skills = water_transformer.detect_stale(registry)
    for report in stale_skills:
        if report.staleness >= water_transformer.staleness_threshold:
            water_transformer.replay_validate(report.skill_id, registry)
```

## 十一、风险评估与应对

### 11.1 技术风险

| 风险 | 可能性 | 影响 | 应对措施 |
|:---|:---|:---|:---|
| LLM忽略蒸馏指令，仍不调用`start_long_term_update` | 中 | 高 | 备选方案：直接在`agent_loop.py`中调用`start_long_term_update`的处理函数，绕过LLM |
| post_validate误判（把合法内容标记为易变状态） | 中 | 中 | 提供豁免机制：特定SOP可标记为`validation_exempt`，同时优化正则表达式 |
| health模型参数不适配实际使用模式 | 中 | 低 | 提供配置化参数，根据实际数据调优；首期可先用默认参数 |
| GA上游更新导致集成点失效 | 低 | 高 | 集成点尽量少且集中；监控GA仓库更新 |
| 火·化误合并（把不相似的技能合并） | 中 | 高 | 保守策略：merge_threshold默认0.7偏高；auto_merge默认关闭；合并产物可split回退 |
| LLM语义判断不稳定（同一对技能，两次判断结果差异大） | 中 | 中 | 语义判断取多次平均值（默认3次）；γ权重仅0.4，不完全依赖语义信号 |
| 合并产物信息丢失 | 中 | 高 | R5完整性校验 + 合并历史完整保留 + split回退机制 |
| 全量扫描O(N²)性能问题 | 低 | 中 | 三层漏斗大幅减少候选对；超过50个技能时只做增量扫描 |
| 回放验证产生副作用 | 中 | 高 | 回放Prompt中强调"Do NOT make any permanent changes"；修改类技能用沙箱执行 |
| LLM修复引入新bug | 中 | 高 | 修复后必须回放验证；max_repair_attempts限制轮次；rollback可回退 |
| 环境画像检测不完整 | 中 | 中 | 画像检测项持续迭代；首版覆盖Python/OS/依赖/API四大类 |
| LLM适配破坏核心逻辑 | 中 | 高 | 适配Prompt强调"ONLY modify environment-specific parts"；适配后回放验证 |
| 变体爆炸（一个技能产生过多变体） | 低 | 低 | 变体按目标环境唯一，同一环境只有一个变体；FireTransformer可合并同环境变体 |

| 风险 | 可能性 | 影响 | 应对措施 |
|:---|:---|:---|:---|
| "成功即记录"导致技能数量膨胀 | 高 | 中 | 金·克修剪机制自然消化；归档阈值可调；火·化合并减少冗余 |

2. `agent_loop.py`中的集成代码因开关关闭而跳过
3. GA恢复原生行为，无任何残留影响
4. `skill_registry.yaml`和`archive/`目录保留，不影响GA运行
