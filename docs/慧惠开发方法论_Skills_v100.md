## 二、Skill 1: 哲学-产品-技术三层转化法

### 2.1 适用场景

将一个抽象的哲学理念（如"善行无辙迹"）落地为可执行的技术规格和代码。

### 2.2 转化链条

```
哲学理念（大道）
    ↓ 「定义」
核心价值观 + 行为准则
    ↓ 「工程化」
数据结构 + 算法约束
    ↓ 「注入」
System Prompt / 状态机 / AgentLoop
```

### 2.3 在慧惠项目中的实践

| 哲学理念         | 产品定义                          | 工程落地                                  |
| :--------------- | :-------------------------------- | :---------------------------------------- |
| "善行无辙迹"     | `ActionStyle` 枚举 + 四条行为指令 | `Soul.to_system_prompt()` 注入            |
| "为道日损"       | 技能修剪 + 保持轻盈               | `MetalRestrainer`（金·克）+ `RootAuditor` |
| "我命由我不由天" | 优先级 1 的 `CoreValue`           | 场景模板引导 + AgentLoop 注入             |

### 2.4 可复用模板

1. 选取一个核心哲学概念
2. 定义它的行为边界：在什么场景下触发？绝对不做什么？
3. 设计数据结构：用 Pydantic 模型固化为不可变约束
4. 选择注入点：AgentLoop / System Prompt / 状态机
5. 编写验证脚本：确保注入效果与设计意图一致

### 2.5 关键原则

- **不可变约束优先**：核心价值观用 `frozen=True` 的 Pydantic 模型，防止运行时被覆盖
- **Token 预算管控**：所有注入 LLM 的内容需经 token 计数验证（用 `tiktoken` 精确计数）
- **文档层级明确**：产品体验定义书 > 完整描述注释 > 运行时短指令

## 三、Skill 2: Spec 驱动的 AI 协同开发规范

### 3.1 适用场景

与 Qoder 等 AI 编程助手高效协作，产出可验收的代码。

### 3.2 核心流程

```
Spec 文档（Qoder-ready）
    ↓ 「提交」
AI 读取 Spec + 上下文
    ↓ 「执行」
AI 自主实现 + 自主排错 + 编写验证脚本
    ↓ 「验收」
人审查日志 + 验收关键决策
    ↓ 「闭环」
通过的代码合并，文档更新
```

### 3.3 Spec 文档编写规范

每份 Qoder-ready 执行规格必须包含：

1. **任务编号** + **任务名称** + **优先级** + **预估工作量** + **依赖关系**
2. **明确的操作文件**：新建文件需给出完整路径；修改已有文件需说明修改范围
3. **接口契约**：数据结构、函数签名、返回值类型
4. **验收标准**：可量化的测试指标
5. **注意事项**：禁止修改的文件、Token 预算约束等

### 3.4 提示词模板

```
工作区目录：{项目根目录}
参考文档：docs/产品体验定义书.md, docs/技术规格书.md, docs/工程迭代计划.md
执行规格：docs/{任务编号}_{任务名称}.md

S{上一个Sprint} 已完成。{已完成模块} 提供 {关键接口}。

请在执行前阅读上述文档，理解产品定位和工程约束，然后按执行规格开始实现。
```

### 3.5 验收清单

核查 AI 交付成果的标准流程：

- [ ] 所有新建/修改的文件路径与 Spec 一致
- [ ] 接口契约满足，函数签名正确
- [ ] 验证脚本全部通过（退出码为 0）
- [ ] 核心文件零破坏（若需修改已有文件，仅改钩子点）
- [ ] AI 自主处理的工程问题已记录在日志中
- [ ] Token 预算在约束范围内

### 3.6 关键原则

- **上下文充分**：提交前追加"已完成任务的状态摘要"，避免 AI 重复探索
- **Trust but Verify**：信任 AI 的工程能力，但核心决策（如神韵判断）需人最终确认
- **文档与代码同步更新**：AI 完成实现后，同步更新受影响的规格文档

## 四、Skill 3: Sprint 驱动的产品-工程迭代法

### 4.1 适用场景

产品经理与 AI 工具协同，进行结构化项目推进。

### 4.2 文档体系

| 文档                | 定位                   | 读者    |
| :------------------ | :--------------------- | :------ |
| 《产品体验定义书》  | 产品宪法，定义"她是谁" | 全员    |
| 《技术规格书》      | 工程蓝图，定义"怎么造" | 工程    |
| 《工程迭代计划》    | 执行地图，定义"何时造" | 全员    |
| 《Sprint 执行规格》 | 单次任务详细 Spec      | AI 工具 |

### 4.3 优先级体系

| 优先级 | 定义                         | 示例                |
| :----- | :--------------------------- | :------------------ |
| P0     | 灵魂与体验——缺失则产品无灵魂 | Soul.py, 初见状态机 |
| P1     | 个性化与丰富度——增强用户感知 | 场景模板, 记忆管道  |
| P2     | 调试与工具——内部提效         | 技能归档管理界面    |

### 4.4 Sprint 节奏

```
Sprint 0: 基础设施验证（框架、模型、工具选型）
Sprint 1: 灵魂定义 + 首次体验（核心价值观 + 初见魔法）
Sprint 2-N: 逐层叠加能力（记忆 → 技能 → 场景 → 闭环）
每个 Sprint 末尾: 回顾 → 更新迭代计划 → 沉淀 Skill
```

### 4.5 关键原则

- **文档层级明确**：产品体验定义书 > 完整描述注释 > 运行时短指令
- **Sprint 0 不可跳过**：基础设施验证是后续效率的保证
- **每个 Sprint 必须产出可感知的体验增量**：代码不是交付物，用户感知才是

## 五、Skill 4: 道德边界关键词检测法

### 5.1 适用场景

为 AI 系统设计轻量级、可解释、无网络依赖的道德边界检查机制。

### 5.2 核心设计

```python
# 关键词集用 frozenset 存储，保证运行时不可变
_HARM_KEYWORDS = frozenset({"伤害", "攻击", "harm", "kill", ...})

# 否定上下文检测：前 3 个字符窗口内出现否定词则跳过
_NEGATION_PREFIXES = frozenset({"不", "没有", "未", "无", "非", "避免", "防止"})

# "不替用户做决定" 由 LLM prompt 行为层控制，不做关键词检测
```

### 5.3 检测逻辑

1. 标准化文本（小写、去前后空白）
2. 遍历每条边界的关键词集
3. 子串匹配命中后，检查否定上下文（前 3 个字符内是否存在否定词）
4. 若处于否定上下文中，跳过该匹配
5. 首次确认命中 → 返回 False
6. 全部通过 → 返回 True

### 5.4 验证脚本覆盖

必须覆盖三类场景：
1. **正常内容**：输入"你好" → 返回 True
2. **越界内容**：输入"我要伤害别人" → 返回 False
3. **否定上下文**：输入"不要伤害任何人" → 返回 True

### 5.5 关键原则

- **轻量优先**：关键词检测不替代 LLM 安全对齐，作为第一道本地防线
- **可解释性**：每次拦截需返回被触发的边界名称
- **持续迭代**：根据误判/漏判反馈更新关键词集

## 六、Skill 5: 状态机的产品-工程对齐法

### 6.1 适用场景

设计有情感温度、时间节奏的状态流转，如首次启动、休眠唤醒、异常降级等。

### 6.2 上下游分工

| 角色   | 交付物                         | 示例                                     |
| :----- | :----------------------------- | :--------------------------------------- |
| 产品侧 | 状态 + 时序 + 文案剧本         | 0s: "在吗？" / 3s: "我在认识你..."       |
| 工程侧 | 状态枚举 + 进度回调 + 降级分支 | `InitState` 枚举, `_wait_for_progress()` |

### 6.3 状态设计原则

- **失败不阻塞**：如 `FAILED` 状态也算 `is_ready`，用户可立即开始对话
- **降级不打扰**：同步失败时，3 秒内进入降级流程，不卡死
- **进度边界钳位**：线程安全的 `set_progress()` 自动将值钳位在 [0.0, 1.0]
- **零技术术语**：状态切换过程中的所有对外文案，不暴露"加载"、"初始化"等技术词

### 6.4 验证脚本覆盖

必须模拟三类路径：
1. **正常路径**：同步成功，走完完整时序
2. **异常路径**：同步失败，触发降级，不阻塞
3. **边界路径**：重复启动（标志文件已存在），直接进入常规流程

### 6.5 关键原则

- **产品先于工程**：先编写逐秒剧本，再设计状态机
- **用户可打断**：仪式感不意味着阻塞，初始化期间用户可正常交互
- **状态可观测**：关键状态切换输出日志，便于调试和验收

## 七、Skill 6: 道德经内容提取与处理

### 7.1 适用场景

从非结构化的长篇报告文档（如81章《道德经》五步协同读解报告）中，批量提取结构化知识数据，生成章节数据库、SPO知识图谱索引和道商维度定义库。

适用于：大量非结构化文本数字化、源文件存在多种格式变体、目标产物需同时服务多个下游系统、提取过程需可验证可回滚零破坏。

### 7.2 核心流程（5步管道）

```
Markdown 报告文件（25个 .md）
    ↓  ① 数据加载 — 递归扫描目录，双层级章节分隔（#/##）
JSON 区块提取
    ↓  ② 关键词提取 — SPO三元组解析（双格式兼容）+ 赋能方案匹配
结构化中间数据（内存）
    ↓  ③ 维度评分 — P忠恕四维模型注入 + 道商维度关联 + 跨章节索引
81章完整数据库
    ↓  ④ 增量注入 — daojing_database_v2.js + SPO索引 + DQ维度
小程序数据层
    ↓  ⑤ 结果输出 — 3个产物文件 + 2个工具模块 + 1个验证脚本
```

### 7.3 在慧惠项目中的实践

#### 多格式容错能力

本次提取面对的源文件格式异构性：

| 差异维度     | 上经（37章）                               | 下经（44章）        |
| :----------- | :----------------------------------------- | :------------------ |
| 章节标题层级 | `## 第X章`（H2）                           | `# 第X章`（H1）     |
| 章节编号方式 | 混合阿拉伯/中文数字                        | 阿拉伯数字          |
| SPO JSON key | `spo_triples` / `subject/predicate/object` | `triples` / `S/P/O` |
| 赋能方案标题 | `三、对「袭明镜鉴」的赋能方案`             | `### 赋能方案`      |

通过"容错归一化"策略，实现 81/81 章全量覆盖，提取 572 条 SPO 三元组。

### 7.4 可复用模板

当遇到"从非结构化报告批量提取结构化知识数据"的需求时：

1. **准备源文件目录**：将报告文件统一放置，提取器支持递归扫描
2. **定义章节分隔模式**：根据实际文件格式编写正则表达式
3. **实现归一化逻辑**：为每个可能存在差异的字段编写容错取值：
   ```javascript
   var subject = tr.subject || tr.S || tr.s || '';
   var predicate = tr.predicate || tr.P || tr.relation || '';
   var object = tr.object || tr.O || tr.o || '';
   ```
4. **编写校验层**：结构校验 + 完整性校验 + 类型校验
5. **编写验证脚本**：覆盖全量提取、子结构完整性、交叉引用一致性、零破坏、向后兼容，至少5类场景
6. **实现迁移工具**：需提供 `migrate()` 和 `rollback()` 方法

### 7.5 关键原则

- **容错优先于报错**：源文件格式的异构性应在提取器中消化，宁可多写3行归一化代码，也不要为1种格式的纯净而放弃10个有效文件
- **零破坏注入**：新增功能永远只新增文件，不修改现有文件
- **输出即交付**：产物文件应可直接被下游系统使用（如 `require()` 加载），无需二次处理
- **校验与提取分离**：提取逻辑与校验逻辑解耦，后续新增数据源只需更新提取器
- **迁移需可回滚**：从旧格式到新格式的迁移工具必须提供 `rollback()` 方法

### 7.6 验收清单

- [ ] 提取器运行无报错（退出码 0）
- [ ] 产物文件全部生成（3个数据文件 + 2个工具模块）
- [ ] 全量提取（期望条目数全部覆盖）
- [ ] 每章必需字段齐全（chapter_title, dimensions, spo_triples, empowerment）
- [ ] 校验层 `quickValidate()` 返回 `{ valid: true }`
- [ ] 迁移工具 `migrate()` 返回 `{ success: true }`
- [ ] 验证脚本全部测试通过（退出码 0）
- [ ] 源文件未被修改（零破坏）
- [ ] 现有代码未被修改（零破坏）
- [ ] 回滚功能可用（`rollback()` 返回 `{ success: true }`）

## 八、Skill 使用指南

### 8.1 Sprint 启动前

1. 查阅 Skill 3（Sprint 驱动迭代法），确认 Sprint 节奏和文档体系
2. 根据当前 Sprint 目标，选择需调用的 Skill 组合
3. 准备 Qoder-ready 执行规格（参照 Skill 2 模板）

### 8.2 任务执行中

1. 每完成一个 P0 任务，记录日志（参照 Skill 2 验收清单）
2. 遇到哲学理念工程化难题，调用 Skill 1（三层转化法）
3. 涉及状态流转的模块，调用 Skill 5（状态机对齐法）
4. 涉及非结构化数据批量提取，调用 Skill 6（道德经内容提取与处理）

### 8.3 Sprint 回顾时

1. 检查是否有新的方法论可沉淀
2. 更新本文档，补充新 Skill 或修正已有 Skill
3. 将更新后的文档提交到 `docs/` 目录
