# Spec驱动的AI协同开发规范

## 一、适用场景

当你需要与Qoder等AI编程助手高效协作、产出可验收代码时，调用本Skill来：

- 将产品需求转化为Qoder可执行的Spec文档
- 指导AI按Spec自主实现、自主排错、编写验证脚本
- 建立"人类审查关键决策 + AI执行工程细节"的分工模式

## 二、核心流程

```
Spec 文档（Qoder-ready）
    ↓ 「提交」
AI 读取 Spec + 上下文
    ↓ 「执行」
AI 自主实现 + 自主排错 + 编写验证脚本
    ↓ 「验收」
人审查日志 + 验收关键决策
    ↓ 「闭环」
通过的代码合并，文档同步更新
```

### 2.1 流程详解

**阶段1 — Spec准备（人）**
1. 确定任务编号、名称、优先级、依赖
2. 明确操作文件：新建给出完整路径，修改说明修改范围
3. 定义接口契约：数据结构、函数签名、返回值类型
4. 设定验收标准：可量化、可自动化验证
5. 标注注意事项：禁止修改的文件、Token预算等硬约束

**阶段2 — AI执行（机）**
1. AI读取Spec和参考文档
2. AI按Spec自主实现代码
3. 遇到错误时AI自主排查修复
4. AI编写验证脚本并确保全部通过

**阶段3 — 验收（人）**
1. 对照验收清单逐项核查
2. 审查AI处理工程问题的决策日志
3. 核心决策（如体验判断）需人最终确认

**阶段4 — 闭环（人+机）**
1. 通过的代码合并到主分支
2. 受影响的规格文档同步更新
3. 沉淀新的方法论到Skills文档

## 三、提示词模板

### 3.1 任务启动模板

向Qoder提交任务时使用以下模板：

```
工作区目录：{项目根目录}
参考文档：{参考文档列表，逗号分隔}
执行规格：{规格文档路径}

S{sprint编号} 已完成。{已完成模块列表} 提供 {关键接口列表}。

请在执行前阅读上述文档，理解产品定位和工程约束，然后按执行规格开始实现。
```

### 3.2 上下文补充模板

若需追加上下文（如已完成任务摘要），使用以下模板：

```
S{sprint编号} 已完成的上下文：
{已完成任务编号} {任务名称} — 已实现 {关键交付物}，对外暴露 {接口列表}
请在执行 {当前任务编号} 时引用上述接口，避免重复实现。
```

### 3.3 占位符说明

| 占位符             | 说明                 | 示例                                         |
| :----------------- | :------------------- | :------------------------------------------- |
| `{项目根目录}`     | 工作区绝对路径       | `D:\GenericAgent`                            |
| `{任务编号}`       | Sprint任务编号       | `S1-3`                                       |
| `{任务名称}`       | 任务中文名称         | `实现INITIALIZING状态机`                     |
| `{sprint编号}`     | 当前Sprint序号       | `1`                                          |
| `{参考文档列表}`   | 需阅读的文档路径     | `docs/产品体验定义书.md, docs/技术规格书.md` |
| `{规格文档路径}`   | 执行规格文件路径     | `docs/Sprint1_执行规格_Qoder_ready.md`       |
| `{已完成模块列表}` | 已完成模块名称       | `Soul.py, soul_prompts.py`                   |
| `{关键接口列表}`   | 对外暴露的接口       | `get_soul(), inject_soul_prompt()`           |
| `{已完成任务编号}` | 已完成的任务编号     | `S1-2`                                       |
| `{关键交付物}`     | 该任务产出的核心文件 | `core/soul_prompts.py`                       |
| `{接口列表}`       | 该任务暴露的接口     | `inject_soul_prompt(), check_response()`     |
| `{当前任务编号}`   | 即将执行的任务编号   | `S1-3`                                       |

## 四、Spec文档编写规范

每份Qoder-ready执行规格必须包含以下六个要素，缺一不可：

### 4.1 任务元信息

```markdown
### {任务编号}: {任务名称}

**优先级**：{P0/P1/P2}
**工作量**：{预估天数}
**依赖**：{依赖任务编号，无则写"无"}
```

### 4.2 操作文件清单

```markdown
#### 操作文件

| 操作 | 文件路径                         | 说明               |
| :--- | :------------------------------- | :----------------- |
| 新建 | core/new_module.py               | 完整模块实现       |
| 修改 | agentmain.py:get_system_prompt() | 在return前注入Soul |
```

### 4.3 接口契约

```markdown
#### 接口契约

- 类/函数名：{名称}
- 签名：{完整函数签名}
- 返回值：{类型及含义}
- 异常：{可能抛出的异常及条件}
```

### 4.4 验收标准

```markdown
#### 验收标准

- [ ] {可量化标准1}（如：验证脚本全部通过，退出码为0）
- [ ] {可量化标准2}（如：to_system_prompt()输出 ≤ 500 tokens）
- [ ] {可量化标准3}（如：消息中不含"加载""初始化"等技术词）
```

### 4.5 约束与禁区

```markdown
#### 约束

- 不修改 {禁止修改的文件/方法}
- Token预算：{限制值}
- 其他硬约束：{列表}
```

### 4.6 规格完整性检查

在提交Spec给AI前，逐项确认：

- [ ] 所有新建文件路径完整且无歧义
- [ ] 修改已有文件的部分明确到方法/行级别
- [ ] 接口契约足以让AI写出正确的函数签名
- [ ] 验收标准可自动化验证（不依赖主观判断）
- [ ] 约束明确标注"禁止修改"的文件和方法

## 五、验收清单

AI交付代码后，按以下清单逐项核查：

### 5.1 文件层面

- [ ] 所有新建/修改的文件路径与Spec一致
- [ ] 未修改Spec标注为"禁止修改"的文件
- [ ] 若需修改已有文件，仅改指定的钩子点，未扩散

### 5.2 接口层面

- [ ] 所有接口契约满足：类名、函数名、签名、返回值正确
- [ ] 对外暴露的接口可通过 `from module import X` 正常导入

### 5.3 验证层面

- [ ] 验证脚本全部通过（退出码为0）
- [ ] 验证脚本覆盖正常路径、异常路径、边界路径
- [ ] 验证脚本使用精确计数工具（如tiktoken，而非估算）

### 5.4 质量层面

- [ ] Token预算在约束范围内（用tiktoken精确计数）
- [ ] 无技术术语泄露到用户可见文案
- [ ] 代码无语法错误，无未处理的编码问题（如Unicode转义）

### 5.5 日志与文档

- [ ] AI自主处理的工程问题已记录在日志中
- [ ] 需要人确认的关键决策已明确标注
- [ ] 受影响的规格文档已同步更新

## 六、关键约束

### 6.1 角色边界

| 人的职责                   | AI的职责             |
| :------------------------- | :------------------- |
| 定义产品体验方向           | 执行工程实现         |
| 审核关键决策（如神韵判断） | 自主排查技术错误     |
| 编写Spec文档框架           | 根据Spec补充实现细节 |
| 最终验收签字               | 编写验证脚本         |

### 6.2 Trust but Verify

- **信任AI的工程能力**：语法、类型、框架用法、错误排查由AI自主完成
- **验证关键决策**：产品体验相关判断（如文案风格、状态流转节奏）需人最终确认
- **验收不可跳过**：人必须逐项走完验收清单，不因"看起来正确"而跳过

### 6.3 上下文充分原则

- 提交每个新任务前，追加已完成任务的状态摘要
- 避免AI重复探索已确定的代码结构和接口
- 参考文档路径必须准确、可访问

### 6.4 文档同步原则

- AI完成实现后，必须同步更新受影响的规格文档
- 验收通过 = 代码 + 文档 + 日志 三者齐全
- 每个Sprint结束时，评估是否有新的方法论需沉淀到Skills文档

### 6.5 Token预算管控

- 所有注入LLM的内容需经token计数验证
- 优先使用tiktoken（cl100k_base编码）精确计数
- tiktoken不可用时，使用字符数 × 1.5 的保守估算

## 七、使用示例

### 7.1 启动Sprint 1任务

```
调用 spec-driven-dev Skill，执行以下任务：

工作区目录：D:\GenericAgent
参考文档：docs/产品体验定义书.md, docs/技术规格书.md, docs/工程迭代计划.md
执行规格：docs/Sprint1_执行规格_Qoder_ready.md

Sprint 0 已完成。GenericAgent 框架提供 AgentLoop、StreamlitShell 基础架构。

请在执行前阅读上述文档，理解慧惠的产品定位和工程约束，然后按执行规格中的 S1-1 开始实现。
```

### 7.2 追加已完成任务的上下文

```
Sprint 1 已完成的上下文：
S1-1 Soul.py — 已实现 Soul/CoreValue/PersonalityDimension 数据模型，对外暴露 get_soul()
S1-2 注入AgentLoop — 已实现 inject_soul_prompt()，在 get_system_prompt() 中调用
请在执行 S1-3 时引用上述接口，避免重复实现。
```
